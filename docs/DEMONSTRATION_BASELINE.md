# LimitAware — bounded workflow demonstration

Date: 2026-10-24. Scope: one raw export, one transformation, one reference-tool
comparison. No application, no manuscript, no deployment, no external messages.
monitsim untouched.

## Question and answer

**Can a small reproducible workflow preserve laboratory result semantics and
remove a documented manual preparation step without changing the established
statistical analysis?**

* **Semantics and preparation:** yes, demonstrated on a real Water Quality Portal
  (WQP) export — 933 rows reduced to 261 analysable records with every excluded row
  accounted for, and a NADA-ready input produced directly.
* **Statistics:** unchanged, by construction. The workflow feeds the same
  established estimator (NADA `cenfit`); it does not alter the numbers when the
  validated input set is the same.
* **What it does change:** which rows are defensible to include. Two documented
  policies on the same file give materially different estimates (median 0.22 vs
  0.061 µg/L). That is a semantic decision the manual workflow makes silently and
  the script makes explicit.

## 2. Numerical reference (NADA Silver)

* **Provenance:** NADA manual, p. 55 — "Silver concentrations in a standard
  solution sent to 56 laboratories as part of a quality assurance program";
  the dataset was used by Helsel and Cohn (1988) to verify software and is
  provided for code validation.
* **Fixture:** n = 56, 34 censored, **12 distinct detection limits**
  (0.1, 0.2, 0.3, 0.5, 1, 2, 2.5, 5, 6, 10, 20, 25), detected values 0.1–560.
* **Documented analysis reproduced** (NADA 1.6-1.2, R 4.6.1):
  Kaplan–Meier `cenfit` gives median 0.20 and mean 12.649 (SE 76.5 reported as sd
  by the summary); values stored in `literature/limitaware/nada_silver_reference.rds`.
* **Licence:** NADA is GPL (≥2); the Silver data are shipped inside that package.
  They are **not** redistributed here: the fixture is regenerated by the R script
  and the raw object is not copied into any package. Any future distribution must
  either depend on NADA at runtime or obtain independent permission.

This fixture validates that the toolchain can run a documented multiple-limit
analysis. It is **not** evidence of messy raw-data ingestion; that is §3.

## 4. Transformation demonstrated

`scripts/limitaware_transform.py` (≈190 lines, stdlib only) produces:

* `canonical.csv` — every one of the 933 source rows, with source row number,
  raw value/unit/limit/type, parsed value, canonical unit, censored flag, method,
  activity type, and a status;
* `nada_input.csv` — obs / censored / source_row / activity_id / limit_role /
  method for the eligible rows only;
* `audit.json` — counts per status and the interpretation rules.

Status counts for the demonstration run (`--fraction Total --unit ug/L
--limit-policy reporting`):

| Status | Rows | Meaning |
| --- | --- | --- |
| eligible | 261 | analysable under the declared policy |
| excluded_fraction:Dissolved | 300 | other fraction, not pooled |
| excluded_limit_policy:mdl | 287 | censored at an MDL, not a reporting limit |
| excluded_qc | 41 | QC activities retained but not analysed |
| unsupported_unit:missing | 35 | no result unit to convert |
| excluded_below_loq | 9 | "Present Below Quantification Limit" — ambiguous, not coerced |

Representative before/after records (`literature/limitaware/workflow_comparison.json`):

| --- | --- | --- | --- | --- |
| 312 | 0.1 | 0.1 (Method Detection Level) | 0.1 µg/L, detected | eligible |
| 335 | *(empty)* | 0.1 (Lower Reporting Limit) | censored at 0.1 µg/L | eligible |

A real wrinkle surfaced during the run: some `ResultMeasureValue` cells contain
`"<0.1"` rather than a blank plus a sign column. The script parses both encodings
and records which one was used. This is exactly the class of ambiguity a
qualifier-preserving workflow must handle.

## 5. Workflow comparison

Two documented preparations of the **same** export:

* **Manual baseline** (`scripts/limitaware_manual_baseline.py`): filter
  Sample-Routine and Total, convert ng/l, mark "Not Detected" as censored, use
  whatever value is in the limit column, drop rows without a limit. This is what
  the export invites; it is not a straw man.
* **Script**: same filters, but limit **types** are distinct; the policy decides
  which role may define the censoring threshold; ambiguous rows are flagged, not
  dropped.

| Criterion | Manual baseline | Script |
| --- | --- | --- |
| Rows entering NADA | 521 | 261 (reporting policy) / 548 (permissive) |
| Censored rows | 302 | 15 |
| Kaplan–Meier median (µg/L) | 0.061 | 0.22 |
| Kaplan–Meier mean (µg/L) | 0.443 | 0.854 (reporting) / 0.432 (permissive) |
| Interpretation decisions recorded | none | 6 status categories + rules in `audit.json` |
| Traceability to source rows | source row kept in export | source row + activity id + limit role + method |
| Limit types distinguished | no | yes |
| Fraction/unit/method conflicts flagged | no (filtered silently) | yes (status per row) |
| Rows silently dropped | 412 | 0 |

**Agreement check:** running the script with the permissive policy (`any`,
which reproduces the manual intent) gives 548 rows and 302 censored versus the
manual 521 rows and 302 censored. The medians agree exactly (0.061 µg/L); the means
differ by 0.011 µg/L (0.432 vs 0.443). The 27-row difference is fully accounted for
by two explicit policy choices, not by error:

* the script **keeps 36 detected rows that have no limit** (a detected value needs
  no censoring threshold), while the manual baseline drops any row without a limit;
* the script **excludes 9 rows flagged "Present Below Quantification Limit"**,
  while the manual baseline keeps them when the value is numeric.

So the estimator itself is unchanged: NADA returns the same median on the same
censored set, and any difference is the documented policy. The contrast in the
table above (15 vs 302 censored) is the semantic fork, not a numerical
improvement. Any claim of better accuracy would be unsupported.

## 7. Decision: **GO (small, scoped)**

A recurring task is demonstrated with real data and a measured semantic fork. The
proposed software is more than a thin wrapper because it owns the semantic layer
(result vs limit entities, limit types, fractions, units, QC, ambiguity,
provenance) that neither NADA nor ProUCL provides, and it emits a validated input
for the established estimator rather than reimplementing it.

**Scope of the smallest useful release:**

1. **One input profile:** WQP `Result/search` CSV (v1). No UCMR, no vendor formats.
2. **Canonical record:** source row id, activity id, analyte, fraction, value,
   unit, censored flag, limit value/unit/type/role, method, activity type, status.
3. **Policy configuration:** which limit role may define censoring; which
   fractions/methods are admissible; unit conversion table. No defaults that mix
   roles or fractions.
4. **Refusal over coercion:** all-censored samples, missing limits, unsupported
   units and ambiguous qualifiers return a status and an explanation.
5. **Exports:** `canonical.csv`, `nada_input.csv`, `audit.json`, and a one-page
   methods note recording the policy actually applied.
6. **Validation:** NADA Silver fixture (n=56, 34 censored, 12 limits); a
   known-truth simulation with multiple limits; re-run equality on identical input;
   the WQP demonstration above.
7. **Dependencies/licence:** Python ≥ 3.10 stdlib only for v1; MIT. NADA used as an
   external reference at validation time, never bundled.

**Explicit non-goals:** new estimators; "improved" estimates; a GUI-first product;
clinical or regulatory decision support; prevalent/ambiguous cases presented as
unambiguous.

**Why not NO-GO:** the task recurs in accessible public data, the semantic layer is
not provided by the existing tools, and the workflow reproduces a documented
reference analysis. **Why not a large GO:** the statistical contribution is zero
by design, the input scope is one profile, and no usability or time-saving claim is
made or measured here.
